# 골든모델 초안 생성 프롬프트 (재사용 템플릿)

`/draft-golden-model` 커맨드 내부에도 포함되어 있지만, 커맨드 없이 즉석에서
Claude에게 골든모델 함수 하나를 짜달라고 할 때도 아래 원칙을 매번 프롬프트에
포함시킬 것. (예: 대화창에서 "이 함수 짜줘"라고 짧게 요청할 때 누락되기 쉬움)

---

## 필수 포함 지침

당신은 지금 SpaceWire(ECSS-E-ST-50-12C) 골든모델의 일부를 작성합니다.
이 초안은 "완성"이 아니라 "검증의 시작점"입니다. 아래 규칙을 반드시 따르세요.

1. **모든 함수/주요 분기에 `# Spec: §X.X.X` 주석을 달 것.** 인용할 스펙 조항이
   떠오르지 않으면, 코드를 짜지 말고 먼저 "이 부분의 근거가 될 조항을 못 찾았다"고
   말할 것.

2. **확신 없는 부분을 그럴듯하게 채우지 말 것.** 다음 형태로 명시적으로 드러낼 것:
   ```python
   raise NotImplementedError("TODO: §X.X.X <구체적으로 뭐가 불확실한지> - 확인 필요")
   ```
   "일단 합리적으로 짜놓고 나중에 고치면 되지"라는 태도가 이 프로젝트에서
   가장 위험한 실수 패턴입니다 — 나중에 이게 버그인지 의도인지 구분이 안 됩니다.

3. **스펙에 없어서 추정한 부분은 추정이라고 밝힐 것.** 예:
   ```python
   # Spec: 명시 없음 (assumed) — §8.5.2.3의 일반 원칙을 유추 적용
   # 근거: FCT와 동일한 흐름제어 원칙이 적용될 것으로 추정. 확인 필요.
   ```

4. **작성 후 다음 3줄 요약을 반드시 함께 제시할 것**:
   ```
   cited 함수: [목록]
   assumed 함수: [목록 + 추정 근거]
   todo 함수: [목록 + 불확실한 이유]
   ```

5. **"완료했습니다" 대신 "초안 작성했습니다, 검증 필요"라고 말할 것.**
   이 초안은 golden_model_confidence 테이블에 기록되어야 하며, 기록 전까지는
   존재하지 않는 것과 같습니다 (추적 안 되는 코드 = 나중에 존재 자체를 잊어버림).

---

## 왜 이렇게 하는가 (근거 — 세션마다 재설명할 필요 없이 이 문서를 링크)

- 초안이 "이미 존재하는 코드"라는 이유만으로 은근한 권위를 얻는 경향이 있습니다.
  나중에 검증할 때 "이게 왜 이렇게 되어 있지?"라고 재조사하는 것보다,
  처음부터 근거를 남기는 게 훨씬 쌉니다.
- 확신 없는 부분을 숨기면, 나중에 spec-arbiter가 "이건 원래 구현되어 있었는데
  왜 틀렸지"라고 헷갈리게 됩니다. TODO로 명시하면 "아직 안 한 것"과
  "잘못한 것"이 명확히 구분됩니다.
